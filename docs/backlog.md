# Backlog

The ideas, polish and edge cases found along the way that the current step doesn't need. They stay here, out of [roadmap.md](../roadmap.md), until the owner makes one of them a step.

## Language

- Lists, and a `for` loop over them.
- Decimal numbers.
- Two functions that call each other (needs a way to declare a function before its body, or hoisting).
- Messages of their own, rather than *unexpected character*, for `1.5` (no decimal numbers in version 1), `;` (one statement per line) and the typographic quotes `“ ”` pasted from a document (seen at step 5); the error already carries the character, so this may be done in the messages alone.

- A function written in another function that uses a variable or a parameter of the function around it: today an unknown name, while the same mistake in a block of the main program is a variable the function doesn't see. And a variable used after a block that held a function declaring the same name: the `let` given is the one of the block, not the closest above. Both already have the error of a function defined in a block, and go away with it (seen in the review of step 7b).
- The result of a built-in function that gives back no value, found by the checks before running rather than while the program runs (`if forward():`, `let steps = turn_left()`): the checker knows these functions, and a beginner may well write the first one to ask whether the robot can move. Today the function runs, then the program stops (seen at step 9).
- A value that is no color written as such in a call of a function that takes one (`start_painting(3)`, `here_is("red")`), found by the checks before running: today the program stops when it reaches the call, since only a variable needs the values to decide (seen at step 9c).
- The words of Python written with a capital, `True`, `False` and `None`: today names that aren't in `snake_case`, so the checker recalls the rule of the names instead of showing `true`, `false` or that there is no empty value (seen at step 6a).

## Interface

- The French translation of the interface, the levels and the manual; the comments of the starting code of the levels too, which stay in English in the level files for now (seen at step 8b).
- The code normalized to NFC in the editor (step 16): a name pasted with its accents decomposed (`côté` written `co` + U+0302 + …) is cut before the accent by the lexer, which reads the combining mark as an unexpected character (seen in the review of step 5).
- The checks given the text of the document of the editor, never a text from elsewhere (step 16), and a test on a document made from a text with `\r\n`: the places of the bridge are those of the text checked, where a `\r\n` is two units, while CodeMirror counts one unit for every line break (seen in the review of step 10a, see [Technical choices](technical-choices.md), Positions).
- The number of steps in the status bar keeping the width of its figures as it grows (10, 100, 1000), so that what follows it doesn't move while a program runs: its figures already have one width (seen at step 12b).
- The column of the cursor in the status bar (step 16) counted in characters, as the core counts and as a learner does: an emoji is one column, while the editor counts two units for it (seen at step 10a).
- A breakpoint set on a line that never starts a step (step 19): the line of an `else:`, of a `function`, a blank line, a comment. `specs.md` says nothing of it, and such a breakpoint would never pause the program. Either the editor refuses it, or it moves it to the next line that starts a step, as VS Code does; the bridge would then give the lines of a program that start a step (seen at step 10c).
- The variables panel once a program has ended without error (step 19): `specs.md` opens it when the program pauses or stops on an error, and says nothing of the end. The bridge gives the calls in progress and their variables at any time, as they were at the last step (seen at step 10c).
- The text of a variable given to the variables panel (step 19): the core shares a text between its variables, but the bridge copies it for each variable of each call in progress (`Run::calls`), 200 calls at most. Measured on 2026-11-15: 96 MB for a program of 13 kB (a function that calls itself, with 500 variables holding a text of 1 000 characters), 210 MB for a text of 100 000 characters written in the program and held by 10 variables. Either the bridge gives the first characters of a text and says that it is cut, or it gives the variables of one call at a time, the one the panel shows (seen in the review of the limit of the texts).
- The description of a built-in function on hover in the editor.
- A melody of success improvised with the owner in Strudel (strudel.cc, live coding of music in the browser, nothing to install), then written as a recipe of `docs/mockups/world-elements/make-sounds.py` or of the Web Audio API; for the polish (suggested at step 11b).
- The contrast of the texts, for the polish: `specs.md` sets no rule, and several texts are under 4.5:1, the AA level of the WCAG (measured on 2026-11-16, at step 12a). In Day Desk: the green of a success (3.5 on the bands, 3.9 on the panels), the comments of the code (4.2, and 3.6 on the current line), the weak text on the background of the application (3.7). In Night Desk: the comments on the current line (3.5), the weak text on the background of the application (4.0). The line numbers in both (2.7 in Day Desk, 3.2 in Night Desk). To compare before and after on the mock-up, then to change in the tokens of `docs/design-system.md`. Set aside by the owner on 2026-11-16: accessibility alone, not needed for now.
- A phone or tablet layout.
- The home screen in the mock-up (step 3): the path painted up to the level to play and drawn as a ghost after it, as the paint and the goal marks of the map.
- The robot of the home screen walking along the path to the stone clicked, or another animation of the choice; to tune with the mock-up.
- The scene of the level to play on the home screen, without giving the solution: a teaser of its goals, the robot saying them, or a funny moment (the robot dozing off, then *"Ah, functions!"*); to discuss with the mock-up.
- The robot as a mascot in the interface, with expressions (a smile, a wink, a level up, a graduation cap) on the success panel, the home screen or the end of a chapter; drafts in the history of step 1b of `docs/mockups/world-elements/`.
- A setting that draws a pattern inside each paint stroke (dots, stripes…), for learners with a color blindness.
- A mouse cursor of our own on the map or the buttons, such as a small pincer of the robot, drawn by hand; never in the editor, whose I-beam stays the one of the system, and it may take away the larger or contrasted cursors that some learners set.
- A divider to drag between the code and the map, as in VS Code: interesting, but it needs a design of its own (limits, double-click to reset, the size saved) and its integration in every screen.
- A choice **Follow the system** for the theme of the settings: secondary for a website.
- **Ctrl+K Ctrl+C** and **Ctrl+K Ctrl+U** to comment and uncomment, as in VS Code, if learners on a QWERTY keyboard miss a shortcut without punctuation. Set aside for now: two sequences to learn instead of one toggle, and a pause inside a sequence lets Ctrl+U reach the browser, which opens the source of the page.
- Export and import of the progress in a file, so that a learner can go on from another computer without a teacher (the level codes are for the teacher alone). A file could circulate between classmates too, but far less easily than a word dictated.
- The message of the error of 200 calls in progress (step 17): the error names the function whose call is refused, which isn't always the one that calls itself without end (when `count` calls `show`, then itself, the call refused may be `show`), while the mock-up says *"paint_side keeps calling itself"*. Either the message says the fact alone, or the interface reads the calls in progress, which stay readable at the error, to name the function that fills them (seen in the review of step 9b).
- The console of step 17 keeping only its last lines (a few hundred): a `print` in a loop that never ends would otherwise fill the memory of the page, however fast the core is (seen at step 9).
- The running of step 17: a `step()` that throws (an error of the bridge, not of the program) must stop the loop of the animation frames and say it, rather than leave the program shown as running; the speed kept as its value in steps per second rather than its place in the list, so that the speed saved between sessions survives a change of the list (seen in the review of the probe of step 4c).
- The five speeds judged with real programs (step 17): a speed counts the steps, the lines run, not the actions of the robot. A program that asks before each move (`while`, `if`, `forward()`) moves the robot once every three steps, so every three seconds at the slowest speed; the fake program of the probe hid it, each of its steps being an action (seen at step 10d, on the probe run by the real machine).
- The preload of Source Code Pro (step 16, with the editor): the page preloads the three fonts, as the design system asks, but no screen shows code before the editor, and its file is 90 kB of the 144 kB of the fonts. Either only the screens that show code preload it, or it loads with a low priority (seen in the review of step 13a).
- A test of the menus of the header in a real browser, once Playwright is in the project (step 17): the keys, the mouse, the focus that closes a menu when it leaves the bar. At step 13b the functions of the keys have tests, and the wiring was tried by a script in a headless Chromium, not kept.
- A test of a panel over the screen in a real browser, once Playwright is in the project (step 17): Escape, the cross, a click on the veil, a press that starts in the panel and ends on the veil, a double click on what opens it, the focus given back. At step 13c the storage and the settings have tests, and the wiring of the panel, of the banner and of the other tabs was tried by a script in a headless Chromium, not kept; Firefox, Safari and a real screen reader (the banner announced when the storage fills up during a visit) are for step 27.
- A migration of what is saved when its shape changes: today a value of another version is ignored, so a new version of the progress would clear it for every learner. To design before the first change of shape of the progress or of the code of a level, at step 21 at the latest: the store reads one version (seen in the review of step 13c).
- The menus of the header in Firefox and Safari (step 27): the bar moves the focus itself and says when the ring of the keyboard shows, so that the browsers agree, but only Chromium was tried at step 13b. To try there: Space on the name of a menu; a menu opened under a still pointer; the menu that grows and goes back. And with a real screen reader: the bar following its cursor.
- The ring of the keyboard on the name of a menu after a Tab pressed in the address bar: the page never hears that key, so the ring only shows at the next one. Asking the browser whether the focus must show (`:focus-visible`) was tried at step 13b and left: it also says yes when the window comes back after a click, since the bar moves the focus itself. To look at again with the three browsers (step 27): the release of the key, which the page may hear.
- In a menu of the header, a letter that jumps to the next row starting with it, and **Home** and **End** on the bar itself, as some menu bars do: left out at step 13b, the menus being short.
- The smallest window, 1280 × 720, on a laptop of 1366 × 768: at 100 % of zoom, the bars of the browser and of the system leave about 1366 × 650 to the page, so a whole class sees the message of a window too small until each learner zooms out or presses F11, and reads smaller texts at 80 or 90 %. A level screen that fits in about 1280 × 620 would spare them: a question of its layout (the map, the panels), to look at with the owner once the map view and the editor exist (raised by the code review of step 13d; the message says what can work there since then).
- A narrow layout of the manual, so that it stays readable in a window smaller than 1280 × 720, down to about 800 pixels wide, where the other screens show their message: as drawn for 1280, the maps of its examples cover their code at 1024. To judge at step 22, with its real content; until then the manual gives way to the message as the other screens (decided on 2026-11-18, step 13d).
- A phone held sideways: from 800 pixels wide, it gets the message of a window too small, whose advice (widen the window, zoom out with Ctrl and −) is of no use to it. Telling a phone by its pointer rather than by its width alone (`pointer: coarse`) is to try on real phones (left at step 13d).
- A test of the messages in place of the screen in a real browser, once Playwright is in the project (step 17): the window that shrinks under a panel and the panel that comes back, an address that doesn't exist, JavaScript turned off, a file of the application that doesn't come and **Try again**, a browser without WebAssembly. At step 13d the rule of the sizes and the script of the page have tests, and the whole was tried by a script in a headless Chromium, not kept. To look at then, in a real window of each browser: the sentence of a window too small right after the window is maximized and brought back (the browser gives the size of a window with its bars a moment after the event, see [Technical choices](technical-choices.md)), and on a desktop that may not say the room its bars take (Wayland); the focus, which goes back to the page, not to what opened it, when a panel is closed after the window shrank under it, and when it was on a row of a menu, which closes.
- The message of a browser too old in a browser that tells the page nothing of a failed start (no `unhandledrejection`, as Firefox before 69): the page stays empty. A wait that starts with the page rather than with an error would cover it, at the price of a false alarm on a slow connection (left at step 13d).
- The icon of the tab in Safari (step 27): it is an SVG file alone; if a version still in use doesn't draw it, add a PNG of 32 pixels beside it.
- The message of a browser too old in a recent browser where WebAssembly is turned off (the Lockdown Mode of Apple, the safest level of Tor Browser): it tells to update a browser that may be the latest, as it would have for JavaScript turned off before it got a message of its own. A page that reads modules but has no WebAssembly could say so (raised by the code review of step 13d).

## Tooling

- A recommendation of the model and effort for each kind of step, to discuss at the retrospective (and to write in `process.md` and the template if it holds). Every step so far ran on Opus 5.5 at high effort; the steps of architecture (the workspace, the interpreter, the bridge), the audits of quality and the refactorings could run on Fable 5.2, if it brings much in good practices and in quality for its cost. Tried from step 4: the model of each step is marked in `roadmap.md`, and step 4a is reviewed by `code-reviewer` on both models; see the lessons of `process.md`.
- The level files read in TypeScript (`smol-toml`) and handed to the core through the bridge, if the weight of the reader in the WebAssembly module becomes a problem: `serde` and `toml` add about 100 kB gzipped to it (measured at step 8b, see [Technical choices](technical-choices.md), Levels). The files would not change; the cost is a second reader of the format.
- A `timeout-minutes` on the jobs of the CI: a test that never ends (a loop waiting for a line the program no longer reaches) would otherwise hold a job for the six hours GitHub allows (seen in the review of step 10c).
- A JSON Schema of the level files, so that VS Code (with Even Better TOML) completes and checks their fields while they are written.
- The commits of `main` up to #35 keep the address their author had then; since 2026-11-14, the commits carry the no-reply address of GitHub. Giving it to the earlier ones means rewriting the history of `main` (every commit changes its identifier, with a forced push that the Git workflow of `CLAUDE.md` otherwise forbids), then asking GitHub Support to purge the old commits, which the pages of the pull requests keep; it is easiest while the repository has no fork and no release. The owner accepts leaving them as they are (decided on 2026-11-14).
- The former name of the GitHub account, left in `Cargo.toml` (`repository`), `design-journal.md`, `docs/github-pages-usage.md` and `process.md`, and in the remote of a local clone: GitHub redirects the old addresses as long as nobody takes that name.
