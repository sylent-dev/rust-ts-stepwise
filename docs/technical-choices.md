# Technical choices

The technical choices of the [roadmap](../roadmap.md), with their reasons.

| Topic | Choice | Reason |
|---|---|---|
| Language core | Lexer, parser, checker and interpreter of the learner's language in Rust, compiled to WebAssembly with `wasm-bindgen` | The owner's choice, and a language implementation is where Rust's enums and exhaustive matching help most. The whole core stays a plain Rust library, tested with `cargo test` without a browser; only a thin crate exposes it to JavaScript. What the core makes public is what that crate uses: a source is checked whole (`program::check`), read line by line for its colors (`lexer::classify_line`), or read up to the cursor for the names that a line written there may use (`names::names_at`, step 20b), while the tokens, the tree, the parser and the walk of the checker stay in the core (closed at steps 15b and 16a), each declared `pub(crate)`: two lints turned on in the core hold it, `unreachable_pub`, which refuses a `pub` that nothing outside can reach, the compiler then refusing such a type in a public signature, and `unnameable_types`, which refuses a `pub` type of a private module that a public signature gives all the same. |
| Execution | The interpreter runs one step, a line of the learner, per `step()` call, driven by the interface at each animation frame, a number of steps per frame set by the speed. `Playback` (`web/src/lib/run/playback.svelte.ts`) is a program played on a map: it holds the run, asks the page for its own frames while something moves, and reads the speed at each of them; `Program` (`level-screen/program.ts`) is the program of a screen, which checks the code of the editor, then plays it on the map shown, and is what the commands **Run**, **Step** and **Reset** ask | An infinite loop of the learner never freezes the page: it keeps running visibly until **Pause** or **Reset**. The same mechanism gives the animation of the robot, the highlighted current line, the pause, the step button and the breakpoints. The edges of `Playback`, written for the bench of step 14, were settled at step 17a (2026-11-22) from the five assumptions that the audit of step 15 found. A run exists only from the **Run** or the **Step** that starts the program to the **Reset** that puts the map back: at rest the map shows the world of its source, the program valid or not, and `source.start()` reads the code as it is at each start. The frames are asked by the `Playback` itself (`frames`, `requestAnimationFrame` by default), one at a time, and taken back on **Reset** and when it is freed, so that no command has to remember to wake a clock and no frame steps a run freed since; `tick` stays public for the tests, which give the frames themselves. One private function runs a step (`#advance`), for the animated path as for the loop of **Instant**: what comes out of a step beside its action is read there (the line printed, `onPrinted`). A breakpoint pauses the program before the line of its next step, read at each frame where that line is lit and nothing moves, and before each step of a batch of **Instant**, so that one set on the line lit while the program runs is followed; **Resume** runs the line paused on (step 19a), and the sounds follow the actions that the map shows (`onAction`, step 18, see Sounds). How the program stopped is told once per run (`onStopped`), as `outcome` takes it, once the last action has ended: `Program` writes the lines printed and the error that stopped the program in the log of its console (`console/console-log.svelte.ts`, step 17e), which only **Run**, **Step** from stopped and **Restore starting code…** clear. The speed is read from outside (`rate`), since it is a setting: the level screen gives the one of the settings (`settings.speed`), read at each frame, so a speed chosen while a program runs is followed at once, in another tab too (step 17b). An **Instant** frame runs whole batches of steps between two looks at the clock, and a batch is a prime number of steps (997): with 1,000, every frame stopped on the same step of any loop whose turn takes 2, 4, 5, 8 or 10 steps, and the robot of `while true:` / `turn_right()` was never seen moving, on a page that answered all the same (measured by the review of the animations of step 17b, the first step where a learner can choose **Instant**). With a prime, where a frame stops in a loop follows the number of its batches, which the clock makes different from a frame to the next; nothing guarantees it by construction, and the three loops of the review were measured again on the page: the four directions, the whole round of the map and the sixteen poses of a square are seen. The line of the next step (step 17c) and the step counter (step 17d) read the same frames. `status` names each case: `ready`, `running`, `paused` (before the first step too), then `ended` for a program that ran to its end, as the core says it, or `failed` for one that an error stopped; `stopped` is either. **Step**, from stopped, only starts the program, paused before its first line (decided with the owner on 2026-11-22: each line is seen highlighted before it runs). The check before running is the screen's, not the `Playback`'s: `Program` checks the text, starts nothing when it has an error and puts the map back, and keeps the text checked for the run to start on. The level screen keeps one `Program` per playground with `kept` (`core/core-ready.svelte.ts`), the half of `fromCore` that makes an object in a `$derived` and frees it once another one has replaced it and once the component leaves, now written once (it remembers every object it made, since one read then replaced before the effects ran is seen by no effect, found by the second review): the map never draws the program of another map. The screen reads its program by a narrow type (`PlayedProgram`: what the map draws, the line, the steps), so that only `Program`, which checks the code, starts it. The code review found that a run kept in a signal was freed twice, or never, when a **Reset** or a **Step** and another playground came in the same batch: in a cleanup, Svelte gives a signal the value it had before the changes of the batch, and `free` runs there. The run is a plain field, and what `status` follows of it a signal of its own (`#started`); the rule is written above `kept`, and tests with effects hold both (`run/playback.svelte.spec.ts`). A step that throws, at a frame or at a **Step**, stops the program and tells the screen (`onBroken`), which lets the page say it: an error of the bridge, never of the program. Rejected: a source whose `start` returns nothing for a program with errors, which would hide the check, and what it reports, in a callback. |
| No panic in the core | Clippy lints that forbid what can panic in the core (`unwrap`, `expect`, indexing, `panic!`), set up with the workspace | A panic aborts the WebAssembly module, and the page with it: every program of a learner, even absurd, must end with an error the interface can show. Taken from rust-exile-market, whose parser follows the same rule. |
| Interface | TypeScript with [Svelte](https://svelte.dev) 5 | A component holds its markup, script and style in one file with little boilerplate, so the repository reads easily; the runes (`$state`, `$derived`) make the reactive values explicit; compiled, with almost no runtime next to the WebAssembly module. React was rejected for its boilerplate and the pitfalls of its hooks, Vue for being a little more verbose, Solid for its smaller community. |
| Pages | [SvelteKit](https://svelte.dev/docs/kit) with `adapter-static`, server-side rendering off, the pages prerendered as empty shells; each screen has its address (`/`, `/levels/18`, `/sandbox`, `/manual`), the one of a level holding its number: the build writes one page per level (`levels/18.html`), their numbers given by `entries` from the list of `web/src/lib/levels/levels.ts`, which reads the folder `web/levels/` and loads the file of a level, or the one of the sandbox, only when its screen asks for it; a link is written with `resolve()`, which adds the path the website is served from, and an address one way, in a link as in a row of a menu: what follows the root of the website (`sandbox`, `levels/18`), never the name of its route, which ESLint refuses; an address without a page gets `404.html`, the fallback page of `adapter-static`, where the application starts as on any page and shows the message of `src/routes/+error.svelte` | The specifications have four kinds of pages (home, level, sandbox, manual), each with its own address so that the manual can be linked: SvelteKit gives the routing and the folder layout every Svelte developer knows, and builds a static website. Svelte with Vite and a router of our own was rejected: less code at first, but a structure of our own to explain. GitHub Pages serves a file for each address and knows no rule of ours, hence a page per level rather than one page that reads the number: tried on 2026-11-17 with the path of the default address (`/rust-ts-stepwise`), the pages, the fonts and the links follow it. The number rather than the stable name in the address is a choice of the specifications (see [Screens](../specs.md#screens)); the list of the levels is the one place that turns a number into a level. The development server serves the folder of the levels only once `web/vite.config.ts` allows it: its addresses start with `/levels/`, as those of the level screens, which answered for them before (found at step 14a, the first screen that reads a level file). |
| Layout of the interface code | `web/src/lib` holds one folder per domain or block of the specifications, each with its components, its pure logic, its state, its saved shape and its tests, and without a sub-folder: `core/` (the bridge, `core.ts` being the only module of the application that reads the one generated in `wasm/`; what loads it in a test and the test of the glue read it too), `map/`, `run/` (a program being played, and its pace), `levels/`, `level-screen/`, `editor/` (the code editor, a block of the level screen that imports `core/` and the root alone), `code/` (the code of each level as the learner left it, which the editor doesn't know: the level screen gives it, and keeps it), `errors/` (the sentences of each error, of the checks and while running, read in the messages with the values that the core gives; the level screen gives them to the editor, and the console reads them), `console/` (the log of the last **Run** of a program and the panel that draws it; the places of its errors follow the code by the changes that the editor says, `CodeChange`), `variables/` (the panel of the variables, which draws what a program played gives of its calls, `run/shown-calls.svelte.ts`; the level screen places it beside the console, under their tabs), `shell/`, `settings/`, `progress/` (the progress of the learner through the levels, step 21a), `storage/`, `page/` (what the page itself holds, and what the application tells it), `styles/`. Its root keeps what no domain owns and every folder may import (`i18n.ts`, `icon.svelte` and `icon-name.ts`, `elements.ts`, `platform.ts`), and imports no folder; the test of the names of the messages lives there too, since it reads them all. The imports go one way: a route imports the folders, never the other way; `core/`, `map/` and `page/` are the base, which imports no screen: beside the root, `core/` imports only `page/`, `map/` only `core/`, `page/` only `styles/` (its tests read what they check the page against: the settings saved, a storage in memory), `styles/` no folder. A file names its neighbor by a relative path (`./name.ts`) and anything else by `#lib/`, always with `import … from`. ESLint holds all of it on those imports (`no-restricted-imports` in `web/eslint.config.js`, the folders read from the disk), and refuses the two other ways to import a file of the project, `import()` and a type written `import('…').T`, which it couldn't follow. `import.meta.glob`, which only reads data (the levels, the Fluent files), names its folder from the root of `web/` (`'/levels/*.toml'`), so that its module can move. The tests of a folder share their helpers in its `test-support.ts`: the module loaded in a test and small files of levels (`core/`), a storage in memory (`storage/`), a world written as it is drawn (`map/`), the scripts of the page read and run (`page/`) | Steps 16 to 22 write most of the interface: a folder per domain says where a new file goes, and the root stays small enough to be read whole. The direction of the imports keeps the core and the map free of the screens that show them: they are tested alone, and a screen changes without them. A path that says whether it stays in its folder shows a new dependency between two domains at a glance, in a review. The rule is checked by ESLint, as the names of the messages are by a test: what only the reviews hold drifts. A check reads what a file imports itself, never what its imports go on to import: the base stays free of the screens only because each folder that it may import is held too, from `core/` down to `styles/`. A folder stays flat because a file has two ways to name another, its neighbor or another folder: a sub-folder would need a third one for its parent, and a domain that grows becomes two folders side by side instead. The test helpers were written again in each file: seven loadings of the module, three storages in memory (step 15f, 2026-11-19). |
| Strictness of the interface code | `web/tsconfig.json` goes beyond `strict`: `noUncheckedIndexedAccess` (`list[0]` and `table[key]` may be `undefined`), `noImplicitOverride`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, and `allowUnreachableCode` set to `false`; `exactOptionalPropertyTypes` and `noPropertyAccessFromIndexSignature` are left out. ESLint reads the types, for every file and not for the components alone (`web/eslint.config.js`): `strictTypeChecked` and `stylisticTypeChecked` of typescript-eslint in place of `recommended`, and the rules that no set holds: `switch-exhaustiveness-check` (a `switch` without `default` names every value of its union; a `default` counts for the others, is refused when it stands for none, and a `switch` on a text or a number has one), `no-unsafe-type-assertion` (an `as` that narrows a type), `require-array-sort-compare`, `eqeqeq` (but for `== null`), and in a component `no-var` and `svelte/prefer-const`, which typescript-eslint turns on for the `.ts` files alone. Three rules are tuned there, each with its reason: a number may be written in a template (`restrict-template-expressions`); a function of one line may call one that gives nothing where it is typed so, and anywhere in a component (`no-confusing-void-expression`); a test may hold an empty arrow function (`no-empty-function`). An exception is a comment on its line with its reason (`// eslint-disable-next-line <rule> -- <reason>`): its form is held by `@eslint-community/eslint-plugin-eslint-comments` in the scripts and by a selector in the markup of a component, one that excuses nothing is an error (`reportUnusedDisableDirectives`), and so is a warning (`--max-warnings 0`). A type that another file imports lives in a `.ts` file (`icon-name.ts`, beside `icon.svelte`). `npm run lint` builds the module of the core and the types of SvelteKit before ESLint, as `npm run check` does | The code followed these rules already, by discipline and by its reviews: turned on, the options of the compiler gave one error, the two sets of ESLint 87 remarks, 16 once the three rules were tuned, and the rules added by hand 4 (three `as`, one `let`), none a defect. But nothing held it there while steps 16 to 22 write most of the interface. The compiler and ESLint now hold the interface as Clippy pedantic and the forbidden indexing hold the core: an `await` forgotten, a condition that can't be false, a value of the core left out of a `switch`. `exactOptionalPropertyTypes` tells a field left out from a field that is `undefined`. In Svelte, handing `undefined` to an optional property is the usual way to hand nothing, and does the same as leaving it out: of its 11 errors, none a defect, 7 were such properties, and each one would have to be written `goals?: Goals \| undefined`, in every component to come (decided with the owner). `noPropertyAccessFromIndexSignature` is a way of writing that adds no safety to `noUncheckedIndexedAccess`. The compiler only greys out the code that nothing reaches unless `allowUnreachableCode` is `false`, and typescript-eslint leaves that code to it in a `.ts` file. A `default` counts in a `switch` as `_` does in a `match` of the core: where every value must be placed, the `switch` has none, or a table typed by its keys holds them; a `default` after every value is the `_` that Rust calls unreachable, and it would take the next value of the core without a word. An `as` checks nothing when the program runs: the stores check what they read with a guard (`isSaved` in `storage/store.ts`), and the rule holds the next ones to it. The stylistic set holds one way of writing (`??`, `?.`, `interface`, the dot notation), which the code followed already: 10 remarks, in the tests and their environment. An exception has its reason as an `#[expect(…, reason = "…")]` of the core has (`allow_attributes_without_reason`), and a rule turned off for a whole file would undo all of this in one line: hence one package more, since ESLint alone holds neither. ESLint reads the types of the `.ts` files and of the script of the component it checks, not what another component exports: a type written in a component reaches the file that imports it unknown, hence its `.ts` file; the handlers written in the markup reach ESLint untyped, hence the wider option of `no-confusing-void-expression` in a component; and what a component hands to another is checked by `svelte-check` alone, as before. Out of reach of them all: what comes from outside (`localStorage`, a level file), which is checked when it is read, the tools only refusing that an `as` gives it a type; the two scripts written in `src/app.html`, which no tool reads and their tests hold; in the markup of a component, an exception that excuses nothing, which ESLint doesn't see there. ESLint reads the types of the generated module and of SvelteKit as the compiler does: without the first, a copy just cloned gave more than a thousand remarks, in every file that reads the core, so the command builds both first, and `npm run lint` went from about 3.4 to about 5.3 seconds (step 15g, 2026-11-20). |
| Level screen | One component for a level and for the sandbox, `web/src/lib/level-screen/level-screen.svelte`, which lays out its header, the code, the map and the panels. Its route loads the file, keeps what the core reads from it in the module (`fromCore` in `core-ready.svelte.ts`: an object made once the core is ready, freed once another replaces it or the screen leaves) and gives the screen what it plays on, a `Playground` (`level-screen/playground.ts`): a stable name, the world at rest, the goals if any, the starting code and the way to start a program. The map draws one object, a `Scene` (`map/scene.ts`): a world, and the program played on it if any; a playground is one at rest, a `Playback` is one while its program plays | The specifications say that the sandbox is the level screen without goal: wired once, a block that joins the screen (the editor, the console, the panels) joins both, and what is saved for a level is saved for the sandbox under its own name. `Level` and `Sandbox` stay two types in the core and in the bridge, where a map of a level without goal must not exist: the adapter is in TypeScript, two small functions. | Styles | Plain CSS, in `web/src/lib/styles/`: the design tokens as CSS variables, `tokens.css` importing one file per kind (`colors.css` with the two themes, `typography.css`, `spacing.css` with the radii, `layout.css`, `motion.css`), `fonts.css`, `base.css` (the window, the keyboard focus, the scroll bars), `band.css` (the class `band-item`, what is clicked in a band) and `button.css` (the class `button`, a button with a text, `is-main` and `is-danger`), all imported by `app.css`, which the root layout loads once; the theme is the attribute `data-theme` of the page; a Svelte component styles its own block, with the tokens and nothing else; a look that the same markup carries everywhere is a component (`shell/icon-button.svelte`), one that different elements share, or that the page itself writes, a class of this folder; the mock-up loads `tokens.css` from the application | The tokens are the vocabulary of the [design system](design-system.md): written once, a value changes in one place, for the mock-up and for the application, which can't drift apart (decided on 2026-11-17; rejected: a copy in the application with a test that compares the two, two files to change at each design decision). One file per kind, as the sections of the design system (decided on 2026-11-17, rather than one file of a hundred lines): a browser follows the imports for the mock-up, and Vite merges and minifies them for the website. The styles of a component are scoped by Svelte, so two blocks never fight over a class name: they can't be shared either, so the links of the home screen and the names of the menus take a class (decided on 2026-11-17, rather than one component that draws a link or a button according to its options: the name of a menu has too many attributes of its own). The stacking order is a list of named layers, `--layer-…` in `layout.css`, rather than figures spread over the blocks that had to name each other in a comment. A button with a text is a class, `button` in `button.css`, gray at rest, amber as the main button (`is-main`), red as the main button of what can't be undone (`is-danger`): a link and a button take it, and the page itself writes one for its message of a file that couldn't load, so the page carries that file; the action of a message adds its larger size (`.button.screen-message-action`, which wins by its two classes rather than by the order of the files). It left the style sheet of the messages at step 16d, with its first button outside a message, the buttons of a confirmation (the audit of step 15, 15h); the messages compared to the pixel before and after, in both themes, at rest and under the pointer. No CSS framework, since the tokens already are the scale that one would bring. |
| Menus of the header | `web/src/lib/shell/menus.ts` holds what a menu is, the state of the bar (its menu, open or not, its lit row) and what each key does to it, as functions that never touch the page; `menu-bar.svelte` draws that state and wires the mouse and the keys; each screen gives its menus to the bar (`level-menus.ts`); a row is of one kind (`kind`): it leads to a page, names the screen already shown, runs a command of the screen (see Commands of a screen), opens beside it the values of one thing to choose from, the one in use marked (`ChoicesRow`, **Speed** and its speeds), or is the thin line between two groups. The bar moves the focus of the keyboard itself, onto the lit row or else onto the name of its menu, and a menu is open only while the bar holds that focus; it follows a focus that arrives otherwise (Tab, a screen reader), and two listeners of the window tell it the keyboard from the pointer; a row that leads to a page is a link, written with `resolve()`; the rows of every menu stay in the page, hidden until their menu opens, and a menu grows and goes back by its styles alone (a CSS transition that includes `display`) | The keys of a menu bar are the part most likely to break, and a function from a state and a key to a state is tested without a browser. One rule for the focus gives one lit row for the pointer and the keys, closes the menu on Tab and in another window, and holds in every browser: the mouse never moves the focus in the bar by itself (Safari gives none to a button), so the bar also says when the ring of the keyboard shows, from the keys and the presses of the pointer that the window hears. The bar remembers the key that ran a row (`ranBy`) and takes its repeats in the listener of the window, which hears a key before what holds the focus does, until the next press of a key: the editor knows nothing of it. |
| Commands of a screen | `web/src/lib/shell/commands.ts` holds what a command of a screen is, written once (`ScreenCommand`: its name, its text, the shortcut shown, those heard without being shown, whether it can run now, what it runs), and the function that finds the command of a key (`commandFor`), which never touches the page; a shortcut (`Shortcut`) is the character that its key writes, or a key named when it writes none, with the keys held, Ctrl meaning Cmd on a computer of Apple; one listener per screen hears every shortcut, on the window (`shell/screen-shortcuts.svelte`), those of the editor included, and hears nothing under a panel or under a message in place of the screen; a row of a menu holds its command and shows its text, its shortcut (`shell/shortcut-keys.svelte`) and its state; the level screen makes its commands once (`level-screen/level-commands.ts`) and gives them to its menus and to the listener; the editor names what the screen may ask it, a closed list (`Edit` in `editor/edits.ts`), and gives the screen the object to ask it by (`Editing`, made by `followEditing` in `editor/editing.svelte.ts`), knowing neither the menus nor the shortcuts; whether the screen shows is read in one place (`shell/current-screen.svelte.ts`), by the listener as by a panel | The audit of step 15 found that a command, its text, its shortcut and its state lived nowhere together, while each will show in four places: a row of a menu, a shortcut, the tip of a button, the panel of the shortcuts (step 17). Built at step 16c (2026-11-21) with the first real commands, those of the menu **Edit**. One listener, rather than the keys of the editor bound in CodeMirror and the others heard elsewhere: a shortcut is the same wherever the keyboard is on the screen, as Ctrl+Enter will be (step 17), no key can run a command twice, and one place reads the state of a command and whether the screen shows. CodeMirror keeps the keys of typing alone: a test compares its bindings, for every computer, with the shortcuts of the commands, so that a ready-made set of keys added later is refused.
