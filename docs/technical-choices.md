# Technical choices

The technical choices of the [roadmap](../roadmap.md), with their reasons.

| Topic | Choice | Reason |
|---|---|---|
| Language core | Lexer, parser, checker and interpreter of the learner's language in Rust, compiled to WebAssembly with `wasm-bindgen` | The owner's choice, and a language implementation is where Rust's enums and exhaustive matching help most. The whole core stays a plain Rust library, tested with `cargo test` without a browser; only a thin crate exposes it to JavaScript. |
| Execution | The interpreter runs one step, a line of the learner, per `step()` call, driven by the interface at each animation frame, a number of steps per frame set by the speed | An infinite loop of the learner never freezes the page: it keeps running visibly until **Pause** or **Reset**. The same mechanism gives the animation of the robot, the highlighted current line, the pause, the step button and the breakpoints. |
| No panic in the core | Clippy lints that forbid what can panic in the core (`unwrap`, `expect`, indexing, `panic!`), set up with the workspace | A panic aborts the WebAssembly module, and the page with it: every program of a learner, even absurd, must end with an error the interface can show. Taken from rust-exile-market, whose parser follows the same rule. |
| Interface | TypeScript with [Svelte](https://svelte.dev) 5 | A component holds its markup, script and style in one file with little boilerplate, so the repository reads easily; the runes (`$state`, `$derived`) make the reactive values explicit; compiled, with almost no runtime next to the WebAssembly module. React was rejected for its boilerplate and the pitfalls of its hooks, Vue for being a little more verbose, Solid for its smaller community. |
| Pages | [SvelteKit](https://svelte.dev/docs/kit) with `adapter-static`, server-side rendering off, the pages prerendered as empty shells; each screen has its address (`/`, `/levels/18`, `/sandbox`, `/manual`), the one of a level holding its number: the build writes one page per level (`levels/18.html`), their numbers given by `entries` from the list of `web/src/lib/levels.ts`, which reads the folder `web/levels/` and loads the file of a level, or the one of the sandbox, only when its screen asks for it; a link is written with `resolve()`, which adds the path the website is served from; an address without a page gets `404.html`, the fallback page of `adapter-static`, where the application starts as on any page and shows the message of `src/routes/+error.svelte` | The specifications have four kinds of pages (home, level, sandbox, manual), each with its own address so that the manual can be linked: SvelteKit gives the routing and the folder layout every Svelte developer knows, and builds a static website. Svelte with Vite and a router of our own was rejected: less code at first, but a structure of our own to explain. GitHub Pages serves a file for each address and knows no rule of ours, hence a page per level rather than one page that reads the number: tried on 2026-11-17 with the path of the default address (`/rust-ts-stepwise`), the pages, the fonts and the links follow it. The number rather than the stable name in the address is a choice of the specifications (see [Screens](../specs.md#screens)); the list of the levels is the one place that turns a number into a level. The development server serves the folder of the levels only once `web/vite.config.ts` allows it: its addresses start with `/levels/`, as those of the level screens, which answered for them before (found at step 14a, the first screen that reads a level file). |
| Level screen | One component for a level and for the sandbox, `web/src/lib/level-screen/level-screen.svelte`, which lays out its header, the code, the map and the panels. Its route loads the file, keeps what the core reads from it in the module (`fromCore` in `core-ready.svelte.ts`: an object made once the core is ready, freed once another replaces it or the screen leaves) and gives the screen what it plays on, a `Playground` (`level-screen/playground.ts`): a stable name, the world at rest, the goals if any, the starting code and the way to start a program. The map draws one object, a `Scene` (`map/scene.ts`): a world, and the program played on it if any; a playground is one at rest, a `Playback` is one while its program plays | The specifications say that the sandbox is the level screen without goal: wired once, a block that joins the screen (the editor, the console, the panels) joins both, and what is saved for a level is saved for the sandbox under its own name. `Level` and `Sandbox` stay two types in the core and in the bridge, where a map of a level without goal must not exist: the adapter is in TypeScript, two small functions. A playground reads its level once, so the map shows as soon as the core is ready, before any program and whether the code has errors or not. What tells the two screens apart in the header (the menus, the mark of the sandbox) is given to the screen beside the playground, not read from it: the header shows before the core has loaded. The wiring was written twice until the quality audit (step 15d, 2026-11-19). |
| Styles | Plain CSS, in `web/src/lib/styles/`: the design tokens as CSS variables, `tokens.css` importing one file per kind (`colors.css` with the two themes, `typography.css`, `spacing.css` with the radii, `layout.css`, `motion.css`), `fonts.css`, `base.css` (the window, the keyboard focus, the scroll bars) and `band.css` (the class `band-item`, what is clicked in a band), all loaded once by the root layout; the theme is the attribute `data-theme` of the page; a Svelte component styles its own block, with the tokens and nothing else, and a look that a link and a button share is a class of this folder; the mock-up loads `tokens.css` from the application | The tokens are the vocabulary of the [design system](design-system.md): written once, a value changes in one place, for the mock-up and for the application, which can't drift apart (decided on 2026-11-17; rejected: a copy in the application with a test that compares the two, two files to change at each design decision). One file per kind, as the sections of the design system (decided on 2026-11-17, rather than one file of a hundred lines): a browser follows the imports for the mock-up, and Vite merges and minifies them for the website. The styles of a component are scoped by Svelte, so two blocks never fight over a class name: they can't be shared either, so the links of the home screen and the names of the menus take a class (decided on 2026-11-17, rather than one component that draws a link or a button according to its options: the name of a menu has too many attributes of its own). No CSS framework, since the tokens already are the scale that one would bring. |
| Menus of the header | `web/src/lib/shell/menus.ts` holds what a menu is, the state of the bar (its menu, open or not, its lit row) and what each key does to it, as functions that never touch the page; `menu-bar.svelte` draws that state and wires the mouse and the keys; each screen gives its menus to the bar (`level-menus.ts`). The bar moves the focus of the keyboard itself, onto the lit row or else onto the name of its menu, and a menu is open only while the bar holds that focus; it follows a focus that arrives otherwise (Tab, a screen reader), and two listeners of the window tell it the keyboard from the pointer; a row that leads to a page is a link, written with `resolve()`; the rows of every menu stay in the page, hidden until their menu opens, and a menu grows and goes back by its styles alone (a CSS transition that includes `display`) | The keys of a menu bar are the part most likely to break, and a function from a state and a key to a state is tested without a browser. One rule for the focus gives one lit row for the pointer and the keys, closes the menu on Tab and in another window, and holds in every browser: the mouse never moves the focus in the bar by itself (Safari gives none to a button), so the bar also says when the ring of the keyboard shows, from the keys and the presses of the pointer that the window hears. A press elsewhere closes the menu from that same listener, since a press on a scroll bar moves no focus. A link keeps what a browser does with it: the middle click, the tab of the manual. A transition written in the styles needs no state for a menu that is closed but still drawn, takes its duration and its curve from the tokens, and turns back by itself when a menu opens again while it closes; a browser that doesn't know it shows the menu at once (decided on 2026-11-17). |
| Panels over the screen | `web/src/lib/shell/panel.svelte` is the `dialog` element of the browser, shown as a modal and stretched over the whole window: the dialog itself is the veil, and the panel a box in its middle; it follows one value, `open`, which Escape, **×** and a click on the veil set at once; the settings are its first content (`web/src/lib/settings/settings-panel.svelte`), opened from a header by `settings-button.svelte`; a choice between a few values (`segments.svelte`) is the radio buttons of the browser, drawn as segments, the fill of the one chosen an element of its own, placed from the widths that the browser gives (`segments.ts`), which slides by a CSS transition | The browser keeps the keys in a modal dialog, makes the screen under it inert and gives the focus back to what opened it: nothing of that to write nor to test. With the dialog as the veil, a click outside the panel is a click on the dialog itself, and the veil needs nothing from the backdrop that the browser draws, which older browsers cut off from the design tokens. The browser only says that a dialog closed a moment after it did (about a frame): the panel sets `open` itself, so that what opens it never finds it half closed. Radio buttons bring one stop for Tab and the arrows between the values without a line of code. A transition written in the styles takes its duration and its curve from the tokens, turns back from where the fill stands and stops for a learner who asked for less motion, without a state of its own; the fill is created in its place, so nothing slides when the panel opens (decided on 2026-11-18). |
| Messages in place of the screen | Their look is a class of the styles, `web/src/lib/styles/screen-message.css`; `shell/screen-message.svelte` draws one in the application. `shell/window-size.ts` says what a window of a size shows (the screen, the message of a window too small, the one of a phone) and what that message tells to do, from where the window stands on its screen and from the computer (`platform.ts`): grow, zoom out or press F11, or zoom out alone; `shell/current-window.svelte.ts` follows the window of the browser (`svelte/reactivity/window`), and the root layout shows `shell/window-message.svelte` in place of any screen: the screen stays in the page under it, out of sight (`visibility: hidden`) and out of reach (`inert`), a panel over it closes its dialog until the screen comes back, and the focus of the keyboard, read before the screen goes away, is given back with it | The rules of the sizes and of what to do are tested without a browser. A window is taken to fill its screen when it is as large as the room that the system leaves to a window, a pixel or two apart: a laptop of 1366 × 768 leaves about 1366 × 650 to the page, and telling its learner to enlarge a window that can't grow would send them nowhere. The browser says that a window changed before it knows the new size of the window with its bars (measured in Chromium on 2026-11-18: the old size at the event, the new one from the next task on), and nothing says when it has caught up: the place of the window is read at the event, then once more 100 milliseconds later. Whether the window could fit once larger isn't computed: the sizes of a window and of its page aren't in the same pixels under a zoom, and a window told to grow that then fills its screen gets the other sentence. A screen kept in the page keeps everything it holds without a line to save and restore it, and hidden rather than removed from the layout, what it scrolled to. A modal dialog left open would make the message itself inert: the panel keeps `open` and only gives the dialog back. What acts on the screen from elsewhere (a run, a shortcut of the window) reads `currentWindow.fit` to stop while the screen doesn't show (step 17). |
| Messages of the page itself | `web/src/app.html` holds three messages, for a browser where the application can't start: JavaScript turned off (a `noscript`), a browser too old, the files that didn't come. A script of the page, written as the one of the theme, watches the application start: a browser without WebAssembly gets its message at once; a file of the application that didn't come, which every browser names as a module it couldn't load, too; after any other error, it waits 3 seconds for the application to start before saying that the browser is too old. The application tells the page when it runs and when its core can't load, through `web/src/lib/startup.ts`. What the page says has an order: what the application asked for stays; what the page found, a file that didn't come, replaces what it only guessed, a browser too old, never the other way. The page is filled when the website is built: `src/hooks.server.ts` hands `lib/page-fill.ts` what `lib/page-parts.ts` lists, the texts from the translation file, the head of the robot, and the styles the messages use, the design tokens and their class, written in the page itself; a message of the page goes over one of the application | A page that needs the application to say that the application can't start says nothing. The texts stay in the translation file and the tokens in their files: nothing is copied by hand, and a name that nothing answers stops the build. With its styles in the page, a message shows in the theme saved even when no other file could load. An error before the start may come from an extension of the browser as well as from a browser too old, and the page can't tell them apart: waiting costs an old browser 3 seconds, and spares the others a false alarm. The script is tested as the one of the theme, in a browser made for the test (`lib/page-startup.spec.ts`), and the page with what the build hands it (`lib/page-fill.spec.ts`), down to each design token that the look of a message uses: the styles of the application fill a gap on a page that loads, so a token missing from the page would only show where nothing else could load. The page of an error asks for its message before the root layout says that the application runs, since Svelte mounts what a component holds before the component: the script gives the same answer in both orders. A copy of the few tokens in the page, kept in step by a test, was rejected: a second place to change. |
| Interpreter | The checked tree is translated once into a flat list of instructions, each with its place in the source, in `crates/core/src/interpreter/` (`compiler.rs` writes them, `machine.rs` runs them up to the end of a step, `memory.rs` holds what each of them changes, `value.rs` and `operators.rs` the values and what the operators compute, `builtins.rs` what the built-in functions do to the world); the machine owns them and keeps an explicit stack of frames (each frame: its function, its next instruction, its variables, its line, and where its own values start among those of the expressions being evaluated), never the Rust call stack; an instruction marks the start of each line, where a step ends, and a step also ends when a function ends, on the line of its call; a function is translated where it is defined, the main program jumping over it; a call leaves its result, a value or none, apart, where the expression around it takes it, for the built-in functions as for the others; the machine also owns the world it runs the program on, which the program changes through `builtins.rs` alone, where a call either acts (an event for the interface, no value) or senses (a boolean, no event); the event of the robot is its action by its name (moved, turned left, picked up…), even when it changed nothing, and an action that fails is no event; the machine takes only a checked program (`program.rs`), and knows nothing of the goals of a level: a run (`run.rs`) holds the machine with the goals of the map it runs on, and checks them on its world once the program has ended, never after an error; each variable keeps the number of the step that wrote it last, which is how the variables panel knows the ones the last step changed; the translation is the only recursion, on a tree whose depth the parser limits | Pausing between two steps, anywhere in nested loops and calls, needs the whole state of the program in data, and the variables panel reads that same data. A step also ends in the middle of an expression, when a call is entered (`let total = double(3) + 1`): a machine that walks the tree would keep references into it, which the bridge can't hold from one animation frame to the next without counting the references of every node (the parser, the checker and their tests rewritten) or leaking the tree at each **Run**; a list that the machine owns resumes at its next instruction (decided on 2026-11-12, instead of walking the tree). The limit of 200 nested calls is the length of the stack of frames: a recursion of the learner can't overflow the stack of the browser. The state of the machine says whether the line highlighted is resumed after a call: only the machine knows it, and a breakpoint pauses once per line run (decided on 2026-11-13). The interface can't find the variables changed by a step by itself: at the speed **Instant**, it would copy them all before each step. A call that acts gives back no value, so it is alone on its line or stops the program: a step reports at most one event. The event names the action and carries nothing else (decided on 2026-11-14): the interface draws the world anyway and reads there what changed, so the core compares no world before and after an action, and a bump has one source, its error, for its animation and its sound. |
| Lexer | Hand-written, line by line, in `crates/core/src/lexer.rs`: the indentation becomes `Indent` and `Dedent` tokens (four spaces more, or back to an enclosing line, anything else is an error that names the two closest levels); the comments are dropped, the place of each comment line being kept aside, so that the parser tells a block of comments from an empty one; any word of letters, digits and underscores, in any alphabet, is a name; the first error stops it | A statement never spans two lines, so reading line by line is enough and keeps the lexer short; no generator (`logos`) for a few dozen tokens. Whether an indented line follows a `:` is left to the parser, which can then say that the `:` is missing on the line above rather than that the next line is indented. Names in any alphabet (`paintSide`, `côté`) are refused by the checker, which recalls the rule of the names without writing the name for the learner, rather than by the lexer, which could only say that a character is unexpected. The highlighting of the editor is decided at step 16. |
| Parser | Hand-written, by recursive descent, in `crates/core/src/parser.rs`: one method per statement, and for the expressions a loop that climbs the priorities of the operators; the tree of `crates/core/src/ast.rs` keeps the span of every node, the one of a statement that opens a block being its line up to the `:`, which is the current line shown while the program runs, and the one of an expression taking the parentheses around it, a name read keeping its own beside it; an `if` holds the list of its branches, so that a long chain of `else if` doesn't deepen the tree; the first error stops it, the lexer's or its own, as one `SyntaxError`; the tree is at most 200 levels deep (parentheses, operators, calls and blocks), the height of each expression being counted as it is built, and the blocks alone nest at most 50 deep, each limit with an error of its own (`ExpressionTooDeep`, `BlocksTooDeep`) | A language this small needs no generator, and a hand-written parser chooses its errors: `=` for `==`, chained comparisons, the words of other languages wherever they are. The depth is limited in the tree, not only in the recursions of the parser: a chain such as `1 + 1 + 1 + …` is parsed by a loop, yet gives a tree as deep as it is long, which would overflow the stack later, in the checker, the interpreter or when the tree is freed. What needs the names of the program (an expression alone on its line that isn't a call, a `break` outside a loop, a function in a block) is left to the checker, which gives every error rather than the first. Measured in the review of step 6a, at 199 levels: the parser alone needs between 64 and 128 KiB of the stack in a release WebAssembly module (between 256 and 512 KiB in a debug one), out of 1 MiB by default; the checker and the interpreter will walk the same tree, so the measure is redone at step 6c, with the blocks. A level of blocks costs more of the stack than a level of parentheses: measured in the review of step 6b, 199 nested `if` needed between 832 and 864 KiB in a debug WebAssembly module (between 384 and 512 KiB for the parentheses), too close to the 1 MiB of the stack, hence the limit of 50 for the blocks, which nobody reaches by hand: four times fewer levels of blocks. Measured again at step 6c in WebAssembly, by linking a module with smaller and smaller stacks until it traps, on the worst case, 50 blocks around an expression of 150 levels: parsing it then freeing its tree needs between 608 and 624 KiB in a debug module (between 144 and 160 KiB in a release one), against 528 to 544 KiB (112 to 128 KiB) for the deepest expression alone, so at least 400 KiB of the default 1 MiB stay free in the debug module that `npm run dev` and `npm test` load. The checker and the interpreter walk the tree after the parser has returned, each with its own need. Step 10c tests the whole through the real module (`web/src/lib/run.spec.ts`): the deepest program of each kind is checked, then run to its end. Measured in its review, in the same way, on the debug module, for the whole way of a program (checked, translated, run, freed): between 464 and 480 KiB for 198 pairs of parentheses, between 528 and 544 KiB for 198 calls of a function one inside the other, between 544 and 560 KiB for 50 blocks around 148 pairs of parentheses, and between 592 and 608 KiB for 50 blocks around 148 such calls, the worst case found: a call costs more of the stack than a pair of parentheses, in the parser as in the checker. At least 416 KiB of the 1 MiB stay free, and it is always the checks, the first to walk the tree, that would run out. The test proves that nothing overflows today; these measures give the margin. |
| Checker | A walk of the syntax tree, in `crates/core/src/checker.rs`, `check(&Program)` giving every error in the order of the source, each a code with its values and its place, as those of the lexer and the parser; where a statement stands (top level, function, loop) is a small value passed down the walk, not a state to restore; a name refused for its form is still taken as declared, a reserved name never is and keeps its one error, as a parameter too, and a function in a block is still checked as a function; the built-in functions and the colors are enums of the core (`builtin.rs`, `color.rs`), which the interpreter and the map reuse, the variables are a stack of open blocks (`checker/scope.rs`), each with the variables declared so far and, read when the block opens, the `let` written in it, plus the variables whose block has ended: a name that isn't a variable there is then one declared further down, one whose block has ended, or unknown, in that order; a function is checked with a stack of its own, the one around it being put aside, and a first pass lists the variables of the main program, wherever their `let` is, to tell a function that uses one; another first pass lists the functions of the program (`checker/functions.rs`), those written in a block included, each with the place of its name and the number of its parameters, the first of a name being the function: a call is above its definition when its place in the source is before that name, which needs no state in the walk and lets a function call itself; a name that a function has is never a variable, so the walk asks the functions before the variables; and every list of words of the language (keywords, words of other languages, built-in functions, colors) is defined by one macro, `word_enum!` | Unlike a syntax error, an error of names doesn't prevent reading what follows, so the learner sees them all at once; taking a refused name as declared keeps one mistake from giving several errors. An error says what the checker knows of the name, never what the learner meant: reading and changing a variable out of its scope give the same error, and only a name that is nowhere tells a read from a change. A name changed without `let` is not taken as declared, unlike a name refused for its form: nothing says that a `let` was meant, so every use of the name keeps its error, each a fact, and a later error would otherwise give the line of a `let` that doesn't exist. A call of a name is a variable called only when that variable exists there: out of its scope, the checker doesn't know that the variable was meant, and says that no function has this name. Every error of a call is on the name of the function, the wrong number of values included: the tree keeps the place of an expression with the parentheses around it, not the one of the call alone. The errors of a name read are on the name in the same way, without the parentheses around it (`let a = (sidse)` underlines `sidse`): the tree keeps the place of the name beside the one of its expression. A name that a function has stays the function, so a variable that takes it has an error at each line that uses it as a variable, and the calls of a second function of the same name are checked against the first: each line is a fact, and they all go away with the one name that is changed. The macro lists each word once, with its variant: written by hand, a word could be forgotten in the list of all of them or in one of the two conversions, and four enums repeated the same code. A crate (`strum`) was rejected for so little. |
| World | The map and the robot in `crates/core/src/world.rs`, a plain Rust model without `serde`: a `Map` of cells, each a wall or a floor with its paint, its item and its passages east and south (the ones north and west being those of its neighbors, so that each passage is kept once, as a boolean), the coordinates as `u8` from the top left; a `Robot` with its direction, the item it carries and one `Option<Tool>`, the brush with its color or the eraser; a `World` that holds both and changes only through the methods of the actions of the built-in functions, which return a `RobotError` (the bump, the item missing or already carried, the robot's state checked before the cell), its sensors being methods too; a level is built with the methods of `Map`, which take the size asked as it is written (so that an error gives it whole) and refuse a paint, an item or the robot on a wall, a wall on a cell that has a paint or an item (the walls are set first, and nothing is lost in silence), and a passage between two cells that aren't both painted | The interpreter (step 9) only calls a method for each built-in function, and the rules of the brush and the eraser are tested without a program. A passage has no color of its own, since each cell draws its half in its own color (decided on 2026-11-12): a boolean is enough, and the rules of the passages are kept by the map alone: a passage is painted between two painted cells, and loses its paint when the eraser crosses it, when neither of its cells is painted any more, or when one of its cells becomes a wall, a cell erased on its own keeping its passages toward its painted neighbors (decided on 2026-11-15, see *Map* in `specs.md`). One `Option<Tool>` rather than two booleans makes a brush and an eraser down together impossible to write. |
| Positions | In the core, a line and a column, both from 1, the column in characters (Unicode scalar values), at the start and the end of each token and error; for the interface, the bridge turns each stretch into its line and two offsets from the start of the source, in UTF-16 code units (`{ line, from, to }`), computed with the source it was given | The core counts as a learner does, accents included, and its tests read as the source is written. CodeMirror counts in UTF-16 code units from the start of the document, where an emoji takes two: the offsets underline an error and place the cursor as they are, and the line is what the console, the status bar and the variables panel write (`Ln 5`). No column crosses the bridge: an error is listed with its line alone, the editor showing its place (decided on 2026-11-10), so nothing would show a column (decided on 2026-11-14). The offsets are those of the text that was checked, as JavaScript indexes it (`text.slice(from, to)`); they are those of the editor only when that text is the one of its document, since CodeMirror counts one unit for every line break, even for a `\r\n` of the text it was given. So the interface always checks the text of the document of the editor, never a text from elsewhere (a level file, a text kept aside). The bridge is the one place where the positions change. |
| Bridge | `crates/wasm` has a type of its own for each thing that crosses to the interface (`check.rs` for the errors of the checks, `position.rs` for their places), built from the type of the core by an exhaustive `match`, and of the same shape: an error is its place and its kind side by side (`{ span, kind }`); `serde-wasm-bindgen` turns it into a plain JavaScript object, and `tsify` generates its TypeScript type from the same Rust type, given back as `Ts<T>`; an enum with values becomes a union told apart by its `code`, in kebab-case, and every field is in camelCase (`rename_all` on a structure, `rename_all_fields` on an enum with values); under each exported function, a function in plain Rust does the conversion, the exported one only making the objects; a level and the sandbox are exported classes (`level.rs`) that keep in the module what the core read and checked in their file, and give plain objects, built again at each call: the starting code, the world of each map (`world.rs`: the cells row by row, a wall or a floor told apart by its `type`, the paint of a cell with its painted passages on its four sides, the robot with the tool it has down, `tool`, absent when none) and the goals that have a cell, a cell to paint having the shape of a painted cell; a file the core refuses throws an `Error` with the sentence of the core; a program being run is an exported class too (`run.rs`), started from a level or from the sandbox with the text of the program, which the core checks again: `step()` gives back a word (what the step showed: nothing, a line printed, the action of the robot by its name), and the line of the next step, whether it resumes its line after a call and the number of steps run are a number or a boolean, read after each step; the line printed, the world, how the run ended (the goals not met, or the error with its place and its kind, `runtime_error.rs`) and the calls in progress with their variables (`value.rs`) are plain objects, built when the interface asks for them | The types of the language know no format and nothing of JavaScript: they stay those of the core, and the bridge is the one place where they change, the positions included. A type written once gives both the object and its TypeScript type, so the two sides can't drift: an error added to the core doesn't compile until the bridge converts it, and its code then appears in the TypeScript union, where a code without message can be refused (step 17). Compared on 2026-11-14, and rejected: exported classes, as the probe of step 4c was (each object a handle to free by hand, and no nested lists); JSON with TypeScript types written by hand (nothing keeps the two sides alike, and slower on small objects); objects built field by field with `js-sys` (verbose, and types by hand too); `serde` and `tsify` derived on the types of the core (the core would depend on the format, and the places kept inside an error would not be converted); the place written in each of the 52 kinds, or flattened beside the code (`serde` then writes a map, and `tsify` an interface that extends a union, which TypeScript refuses: two attributes and a type named by hand, for an object one level flatter). The `into_wasm_abi` of `tsify` is deprecated for a memory leak: `Ts<T>` is its form to use. Measured on 2026-11-14 in Node.js 24 with the real machine: an object costs 100 to 200 ns to build, which nothing notices for what is rare (the errors after a pause in the typing, the map once per frame, the variables at a pause); a step giving back an object would run 8 million steps per second, where a step giving back a word runs 42 million. So a step gives back a word (decided on 2026-11-14), and the loop of **Instant** reads a number after it: the line of the next step, which is nothing once the program has stopped, so that one read tells both the end of the loop and the line a breakpoint looks at. The line printed is kept in the bridge until the next step, the only thing it keeps: the console reads it and drops its oldest lines itself, where a list kept in the module would have to be bounded there. Measured on 2026-11-14 in Node.js 24 on the map of the sandbox, in release, in million steps per second for a program of the robot, of `print` and of computation alone: 42, 22 and 32 for the step alone; 37, 12 and 28 with the line printed and the next line read, the loop of the level screen; 33, 11 and 25 with a breakpoint as well, on a line the program runs. Having every step of a frame run by one call would be 10 to 20 % faster again, the loop, the breakpoints and the time given to a frame moving into the core: kept in reserve. A whole number of the program crosses as its digits, in a value as in an error: a number of JavaScript holds them exactly only up to 2^53, `serde-wasm-bindgen` refuses the others, and nothing computes with them on the other side, where the variables panel and the messages write a text. A value gives its type beside its text, which tells the text `3` from the number 3 and lets the panel draw each in its way. The errors of the robot have each their code among the others, since each has its message, and the limits of the language (200 calls, 1 000 characters for a text joined and for a line of `print`, and in the checks the 200 levels of an expression, the 50 of the blocks and the largest number a program writes, as its digits) cross with the errors that they stop, so that no message repeats a number of the core. The function in plain Rust is the one `cargo test` calls: a JavaScript object can only be made in WebAssembly, where the tests from TypeScript call the exported one.
